# Предложения по улучшению проекта

**Статус:** документ для обсуждения.  
**Важно:** перечисленные ниже предложения пока не реализованы и не изменяют текущую логику формирования отчётов.

## Основание для анализа

Проверены рабочие модули:

- `main.py`;
- `photos_processor.py`;
- `generate_folder_list.py`;
- `analyze_numbering.py`.

Также изучены шаблоны и примеры JSON-манифестов в `output/`. Синтаксис рабочих Python-файлов проверен командой `py_compile`.

## Приоритет 1 — надёжность результатов

### 1. Вынести конфигурацию из исходного кода

**Проблема.** В `main.py` и `generate_folder_list.py` жёстко указаны абсолютные пути к шаблону, Excel-каталогу и папке исходных объектов. Например, `SOURCE_DIR` указывает на профиль конкретного пользователя Windows.

**Риск.** Проект не переносится на другой компьютер без редактирования исходников; легко случайно обработать не тот набор данных.

**Предложение.** Добавить `config.toml` или `.env` и аргументы командной строки для:

- пути к DOCX-шаблону;
- пути к Excel-каталогу;
- каталога с объектами;
- выходного каталога;
- списка папок/режима пакетной обработки;
- режима обновления полей Word через COM.

**Ожидаемый эффект.** Воспроизводимый запуск без изменения `.py`-файлов.

### 2. Заменить `print()` на модуль `logging`

**Проблема.** Рабочие модули выводят состояние и ошибки через `print()`.

**Риск.** Нет журнала выполнения, уровней важности, времени событий и контекста конкретной папки/файла. После пакетной обработки трудно расследовать ошибки.

**Предложение.** Настроить единый логгер с выводом в консоль и файл `output/logs/`, использовать уровни `INFO`, `WARNING`, `ERROR`, `DEBUG`.

**Ожидаемый эффект.** Понятная диагностика и сохранённая история пакетных запусков.

### 3. Ввести явный результат обработки каждой папки

**Проблема.** Часть исключений перехватывается и преобразуется в пустой `DataFrame`, `False` или простой текст в консоли. Основная функция продолжает работу, но итоговый документ может оказаться неполным.

**Риск.** Отчёт может выглядеть сформированным, хотя таблица, схема или фото не вставились.

**Предложение.** Использовать структуру результата с полями `status`, `warnings`, `errors`, `output_file`, `processed_tables`, `processed_photos`; отдельно обозначить критические и некритические ошибки. В конце пакетного запуска формировать сводный JSON/CSV.

**Ожидаемый эффект.** Контролируемая приёмка результатов и понятный статус каждого объекта.

### 4. Безопасно заменять плейсхолдеры Word без уничтожения форматирования

**Проблема.** В нескольких местах применяются присваивания `paragraph.text = ...` и `cell.text = ...`. В `python-docx` это пересоздаёт текстовые прогоны и может удалить форматирование, поля, нумерацию и часть структуры ячейки.

**Риск.** Потеря стилей, полей `SEQ`, нумерации, форматирования и содержимого в шаблоне.

**Предложение.** Создать общий модуль работы с DOCX-плейсхолдерами, который заменяет текст на уровне `runs` и умеет обрабатывать плейсхолдеры, разбитые между несколькими прогонами. Для ячеек — заменять только нужные прогоны вместо полной очистки `cell.text`.

**Ожидаемый эффект.** Стабильное сохранение оформления шаблона.

### 5. Убрать рискованную модификацию внутреннего XML таблиц

**Проблема.** `fill_table_data_keep_structure()` удаляет строки через `table._element.remove(...)`, то есть через внутреннее API `python-docx`.

**Риск.** Возможны повреждения таблиц с объединёнными ячейками, нестандартными стилями или сложной структурой шаблона.

**Предложение.** Согласовать стратегию таблиц: либо создавать отчётные таблицы заново в строго определённой точке, либо использовать проверенный шаблон строки и копирование XML с тестами на объединённые ячейки.

**Ожидаемый эффект.** Меньше повреждений DOCX на вариативных шаблонах.

### 6. Сделать обновление полей Word управляемым и безопасным

**Проблема.** В конце `main.py` поля обновляются через `win32com` и установленный Microsoft Word. При ошибке COM выводится предупреждение, но пользователь может не заметить, что нумерация не обновилась.

**Риск.** На ПК без Microsoft Word или при занятом Word-процессе документ может содержать неактуальные поля `SEQ`.

**Предложение.** Добавить флаг `--update-fields`/настройку, явную проверку наличия Word, `finally` для гарантированного закрытия COM-объектов, а также статус обновления полей в JSON-манифесте.

**Ожидаемый эффект.** Предсказуемое поведение на разных рабочих местах.

## Приоритет 2 — качество входных данных и обработки

### 7. Централизовать чтение Excel и валидацию схем

**Проблема.** Логика поиска заголовков и обработки файла ширины реализована отдельно в `main.py` и `photos_processor.py`.

**Риск.** Дублирование расходится со временем: таблица ширины в отчёте и фото минимальной/максимальной ширины могут рассчитываться по разным правилам.

**Предложение.** Вынести чтение ширины и других тематических Excel-файлов в единый модуль. Добавить валидацию обязательных колонок, понятные сообщения об ожидаемом формате и тестовые Excel-фикстуры.

**Ожидаемый эффект.** Одинаковая интерпретация данных во всех частях отчёта.

### 8. Ввести строгие правила выбора файлов

**Проблема.** Excel-файлы и папки фото выбираются по подстрокам в имени; при нескольких совпадениях используется первый найденный элемент файловой системы.

**Риск.** При дублирующихся файлах или старых версиях в папке может быть выбран неверный источник.

**Предложение.** Для каждого типа данных описать правила: точный шаблон имени, допустимое число файлов, приоритет версии/даты; при неоднозначности завершать обработку папки предупреждением или ошибкой.

**Ожидаемый эффект.** Исключение случайного выбора файлов.

### 9. Убрать необъяснимые значения по умолчанию

**Проблема.** Если не удаётся определить длину дороги, обработчик общих видов использует `3600` метров; для фото прочности пикет подставляется как `ПК0+000`.

**Риск.** В отчёт могут попасть правдоподобные, но недостоверные сведения.

**Предложение.** Не подставлять значения без подтверждённого источника. Вместо этого оставлять явную отметку «не определено» и добавлять предупреждение в манифест; автоматические значения разрешать только отдельной настройкой.

**Ожидаемый эффект.** Снижение риска фактических ошибок в итоговом отчёте.

### 10. Расширить обход плейсхолдеров

**Проблема.** Текущий поиск охватывает основные абзацы и таблицы документа, но не колонтитулы и другие контейнеры Word.

**Риск.** Часть плейсхолдеров в шаблоне может остаться без обработки.

**Предложение.** Добавить единый обход абзацев и таблиц в теле, верхних/нижних колонтитулах и вложенных таблицах. Перед генерацией выполнять проверку обязательных плейсхолдеров шаблона.

**Ожидаемый эффект.** Раннее обнаружение несовместимости шаблона.

### 11. Ограничить размеры и форматы изображений

**Проблема.** Фото вставляются напрямую; отсутствуют централизованные проверки повреждённых, слишком больших или неподдерживаемых файлов.

**Риск.** Большой итоговый DOCX, переполнение памяти, сбои при вставке отдельных фото.

**Предложение.** Добавить проверку через Pillow, нормализацию ориентации EXIF, ограничение размера/разрешения, единый набор поддерживаемых расширений и журнал пропущенных изображений.

**Ожидаемый эффект.** Меньшие и стабильнее формируемые документы.

## Приоритет 3 — поддерживаемость и поставка

### 12. Разделить крупные модули по ответственности

**Проблема.** `main.py` совмещает конфигурацию, чтение Excel, поиск метаданных, форматирование Word, извлечение изображений, генерацию отчёта и управление COM.

**Риск.** Высокая сложность изменения одной функции без побочных эффектов.

**Предложение.** Постепенно выделить модули: `config.py`, `excel_readers.py`, `docx_placeholders.py`, `report_generator.py`, `word_fields.py`, `models.py`.

**Ожидаемый эффект.** Упрощение тестирования и локальных доработок.

### 13. Добавить автоматические тесты

**Проблема.** В проекте есть исследовательские и ручные тестовые скрипты, но отсутствует единый набор автоматизированных тестов.

**Предложение.** Добавить `pytest`-тесты на:

- преобразование пикетов;
- поиск и замену плейсхолдеров в нескольких `runs`;
- загрузку каждого типа Excel;
- выбор min/max ширины;
- структуру JSON-манифеста;
- обработку отсутствующих файлов.

**Ожидаемый эффект.** Безопасный рефакторинг и быстрый контроль регрессий.

### 14. Добавить корневой `requirements.txt` или `pyproject.toml`

**Проблема.** В корне нет файла с зависимостями. Найденный `requirements.txt` расположен среди тестовых файлов и записан в UTF-16.

**Предложение.** Зафиксировать рабочие зависимости в корне проекта в UTF-8; по возможности создать `pyproject.toml` с минимальной информацией о проекте, версиях Python и командах разработчика.

**Ожидаемый эффект.** Повторяемая установка окружения.

### 15. Убрать или архивировать дубликаты и временные материалы

**Проблема.** В корне расположены папки `ok1`, `ok2`, «тестовые скрипты», «тестовые скрипты-2», Poppler-релизы и выходные файлы.

**Риск.** Непонятно, какой код является актуальным; поиск по проекту выдаёт старые реализации.

**Предложение.** Явно отделить `src/`, `tests/`, `tools/`, `examples/`, `archive/`, `output/` и добавить `.gitignore` для временных/сгенерированных файлов.

**Ожидаемый эффект.** Чище структура и меньше ошибок при сопровождении.

### 16. Инициализировать Git и определить правила версионирования

**Проблема.** Корень проекта не является Git-репозиторием.

**Предложение.** Инициализировать Git, добавить `.gitignore`, фиксировать изменения небольшими коммитами, помечать версии шаблонов и формата входных Excel.

**Ожидаемый эффект.** Контроль истории, удобный откат и безопасная совместная работа.

## Рекомендуемая последовательность обсуждения и реализации

1. Согласовать формат конфигурации и правила выбора исходных файлов.
2. Согласовать, какие ошибки блокируют выпуск отчёта, а какие являются предупреждениями.
3. Исправить замену плейсхолдеров и работу с ячейками Word без потери форматирования.
4. Ввести журналирование и итоговый статус обработки папок.
5. Централизовать обработку Excel/фото, после чего добавить тесты.
6. Выполнить структурный рефакторинг и подготовить воспроизводимую установку.
