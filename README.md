# Road Inspection Automation

Python-проект для пакетного формирования Word-отчётов по обследованию автомобильных дорог на основе Excel-данных, Word-шаблона и фотоматериалов.

## Возможности

- обработка одной или нескольких папок объектов дорожного обследования;
- загрузка метаданных дороги из Excel-каталога;
- заполнение плейсхолдеров DOCX-шаблона;
- формирование таблиц по продольной и поперечной ровности, дефектам покрытия, прочности и ширине проезжей части;
- извлечение схемы ширины из XLSX и вставка в Word;
- добавление фото кернов и шурфов, прочности, минимальной/максимальной ширины и общих видов дороги;
- сохранение итогового отчёта `.docx` и JSON-манифеста с результатами обработки;
- диагностика нумерованных списков и полей Word.

## Основной поток обработки

```text
Папка объекта
  ├─ Excel-файлы обследований
  ├─ папки с фотографиями
  └─ название объекта
          │
          ▼
main.py
  ├─ загружает Excel-каталог объектов;
  ├─ находит метаданные по названию папки;
  ├─ копирует DOCX-шаблон;
  ├─ вставляет текст, таблицы и схему из Excel;
  ├─ вызывает photos_processor.py;
  ├─ сохраняет итоговый DOCX;
  └─ создаёт JSON-манифест в output/.
```

## Структура проекта

```text
road_inspection_automation/
├─ main.py                                  # основной генератор отчётов
├─ photos_processor.py                      # обработка и вставка фотографий
├─ width_data.py                            # единое чтение и анализ Excel-данных ширины
├─ generate_folder_list.py                  # вывод списка папок для пакетной обработки
├─ analyze_numbering.py                     # диагностика нумерации и плейсхолдеров DOCX
├─ template/
│  ├─ template_6.docx                       # используемый по умолчанию шаблон
│  └─ *.xlsx                                # Excel-каталоги объектов
├─ output/                                  # созданные отчёты и JSON-манифесты
├─ ok1/, ok2/                               # сохранённые варианты кода
├─ тестовые скрипты*/                       # исследовательские и вспомогательные скрипты
└─ Modelfile                                # конфигурация локальной модели Ollama
```

Рабочими модулями считаются файлы в корне проекта: `main.py`, `photos_processor.py`, `generate_folder_list.py` и `analyze_numbering.py`. Каталоги `ok1`, `ok2` и тестовые скрипты содержат исторические или экспериментальные варианты.

## Требования

### Платформа

- Windows 10/11;
- Python и виртуальное окружение проекта;
- Microsoft Word — **необходим только для финального обновления полей Word** через COM (`win32com`), например полей `SEQ`.

Основная обработка Excel, Word-документа и изображений выполняется без COM, но финальный шаг обновления полей пытается открыть документ в установленном Microsoft Word.

### Python-зависимости

Код использует следующие пакеты:

- `pandas`;
- `numpy`;
- `openpyxl`;
- `python-docx`;
- `Pillow`;
- `lxml`;
- `pywin32`;
- `python-dateutil`.

В текущей версии проекта корневой `requirements.txt` отсутствует. Перечень используемых версий найден в `тестовые скрипты-2/requirements.txt`; перед развёртыванием рекомендуется подготовить отдельный корневой файл зависимостей в UTF-8.
## Настройка путей и запуска

Рабочие пути больше не задаются в исходном коде. Приоритет источников настроек: аргументы командной строки → TOML-файл → переменные окружения `ROAD_INSPECTION_*`.

1. Скопируйте `config.example.toml` в локальный `config.toml` (он намеренно не отслеживается Git).
2. Укажите пути `template_path`, `catalog_path`, `source_dir` и `output_dir`.
3. Запустите генератор с `--config .\config.toml`.

Пример пакетной обработки подпапок источника:

```powershell
& .\venv\Scripts\python.exe .\main.py --config .\config.toml
```

Пример явного запуска без TOML и без Microsoft Word/COM:

```powershell
& .\venv\Scripts\python.exe .\main.py `
  --template "D:\data\template\template_6.docx" `
  --catalog "D:\data\template\catalog.xlsx" `
  --source "D:\data\objects\Проезд Энергетиков" `
  --output-dir "D:\data\output" `
  --skip-com-update
```

Для обработки конкретных объектов можно повторять аргумент `--folder`. Параметр `--process-subfolders` заставляет интерпретировать `--source` как каталог с объектами.

## Подготовка входных данных

### Excel-каталог

Каталог должен содержать сведения, по которым название папки объекта можно сопоставить с дорогой. В `main.py` используются, в частности, колонки:

- `№ п/п`;
- `Участок` или вариант названия номера участка;
- `Наименование дороги`;
- `Балансодержатель автомобильной дороги`;
- `Идентификационный номер`;
- одна из возможных колонок протяжённости: `Протяженость(Линейная)`, `Протяженость`, `Протяженность`, `Длина` и похожие варианты.

### Excel-файлы в папке объекта

Поиск файлов происходит по фрагментам имён. Для полного отчёта ожидаются файлы, содержащие следующие слова:

| Тип данных | Фрагмент имени Excel-файла |
| --- | --- |
| Продольная ровность | `Продольная ровность покрытия` |
| Поперечная ровность | `Поперечная ровность покрытия` |
| Дефекты покрытия | `Дефекты покрытия` |
| Прочность | `Прочность дорожной одежды` |
| Ширина | `Ширина проезжей части` |

Файл ширины используется и для таблицы, и для извлечения схемы, и для выбора фотографий с минимальным и максимальным значением ширины. Чтение таблицы и поиск min/max централизованы в `width_data.py`, поэтому оба сценария используют одинаковое распознавание заголовков, чисел с запятой и координат.

### Папки с фотографиями

Обработчик ожидает следующую структуру/соглашения об именовании:

- `Фотоматериалы кернов и шурфов/Образец № <номер>/` — фото кернов и шурфов;
- папка, в имени которой есть `измерения прочности` — фото прочности;
- папка `Фотоматериалы <название_папки_объекта>` — общие виды дороги;
- изображения с расширениями `.jpg`, `.jpeg`, `.png`; в отдельных сценариях также поддерживаются `.bmp` и `.tiff`.

Для фото прочности сначала ищется файл, в имени которого есть `1 замер`; при отсутствии используется первое найденное изображение.

## Результаты обработки

Для каждого объекта создаются:

- `<название>_report.docx` — итоговый Word-отчёт;
- `<название>_report.json` — манифест обработки.
- `logs/run_<дата-время>.log` — журнал запуска;
- `run_manifests/run_<дата-время>.json` — сводный статус всех папок пакетного запуска.

Пример структуры JSON-манифеста:

```json
{
  "folder": "Проезд Энергетиков",
  "output_file": "...\\132_Проезд Энергетиков_report.docx",
  "processed_tables": [
    {
      "placeholder": "{{ТАБЛИЦА_ПРОДОЛЬНАЯ_ДАННЫЕ}}",
      "status": "success",
      "rows": 10,
      "file": "1. Продольная ровность покрытия.xlsx"
    }
  ]
}
```

## Ограничения текущей реализации

- основной сценарий запуска использует TOML/CLI-конфигурацию и сохраняет журнал выполнения; часть старых рабочих функций пока продолжает выводить подробную диагностику через `print()`;
- поиск плейсхолдеров выполняется в основных абзацах и таблицах, без гарантированного обхода всех контейнеров Word;
- часть операций с текстом ячеек Word может сбрасывать форматирование;
- выбор Excel-файла и фотопапки основан на фрагментах имён и требует соблюдения соглашений об именовании;
- финальное обновление Word-полей зависит от установленного Microsoft Word и COM;
- добавлены базовые проверки `unittest` для конфигурации и сводного манифеста; корневой файл зависимостей пока отсутствует.

Подробный список предложений доработки и их приоритетов см. в [IMPROVEMENTS_FOR_DISCUSSION.md](IMPROVEMENTS_FOR_DISCUSSION.md).

## Проверка синтаксиса

Перед внесением изменений в код можно выполнить базовую проверку синтаксиса:

```powershell
& .\venv\Scripts\python.exe -m py_compile .\main.py .\photos_processor.py .\generate_folder_list.py .\analyze_numbering.py .\app_config.py .\logging_utils.py .\run_manifest.py
& .\venv\Scripts\python.exe -m unittest discover -s .\tests -v
```

Эта команда проверяет синтаксис и импорты на уровне компиляции, но не запускает генерацию отчётов и не проверяет фактические входные Excel/DOCX-файлы.
